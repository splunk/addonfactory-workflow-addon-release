# Resolve FOSSA credits

Use this skill only after a FOSSA credits CI run has produced a review artifact. All licensing and copyright decisions require human review. The skill gathers evidence and drafts exact-version rules; it does not approve or invent legal conclusions.

## Inputs

- The failed `fossa-credits-<version>` CI artifact from the PR being reviewed.
- The TA repository's `.fossa-license-resolutions.json`.
- The exact FOSSA attribution response and request metadata in the artifact.

## Review process

1. Confirm the artifact's `credits-summary.json` scan revision is the revision reported by the same run's `fossa-scan` job. Open its FOSSA report link and retain the revision and raw-report SHA as provenance.
2. Read `credits-review-queue.txt` and `credits-diagnostics.txt`. Each entry names the exact component, version, and unresolved fields or validation issue.
3. For each unresolved exact name/version, inspect the matching upstream source or package artifact. Establish the applicable license text, copyright holder, and any separate notices from that exact version. Record immutable source URLs or repository paths and a concise rationale in the TA-owned resolution rule.
4. Edit only `.fossa-license-resolutions.json`. Preserve existing rules. Do not edit the generated raw report, request metadata, draft, or final JSON.
5. Re-run generation against the same artifact locally when investigating. The raw report, request metadata, and draft must remain together because the draft carries checksums and sibling-file provenance.
6. Commit the resolution-config change for normal PR review. The next CI run performs a fresh scan, regenerates the preview from that run's exact revision, and checks the new rules.
7. Keep unresolved fields explicit. Do not copy a decision from a different package version without researching the exact version. Do not exclude components based on development labels or assumptions about packaging.

## Resolution rule shape

Rules match the exact FOSSA `name` and `version`. A rule should include only researched overrides, plus a reason and source evidence. For example:

```json
{
  "name": "example-package",
  "version": "1.2.3",
  "license": "MIT",
  "copyright_holder": "Example Authors",
  "license_text": "...complete license terms...",
  "reason": "Reviewed the license and copyright files in the 1.2.3 source archive.",
  "source": "https://example.org/example-package/tree/v1.2.3/LICENSE"
}
```

The example is illustrative only and must not be copied as a real decision. Keep the versioned output generated by CI; hand-editing generated public credits is not a resolution.
